# 决策评审：AI 浏览器技术底座

日期：2026-11-11

## 议题

采用“现有 Chromium + 本地执行代理 + 可插拔能力提供器 + MCP 兼容层”开发 AI 浏览器，后续替代 BrowserOS neo；挑战处理采用 `ddddocr -> AI 恢复 -> 人工接管`，全程保留动作账本。

## Stage 1：独立反驳

两名独立红队分别从挑战状态机/实现成本和安全/产品边界执行只读评审。以下仅保留通过机制、量级、可证伪、可行动四项门槛的意见。

### 致命问题

1. **“图片挑战”不是明确支持范围。** OCR 只能覆盖文字图片子集，点选、滑块、旋转等需要独立检测、定位和动作适配。动作：首版只注册通用文字图片提供器，其余类型进入 AI 恢复，不宣称统一识别。
2. **检测、分类、识别是三个独立问题。** `ddddocr` 不负责发现挑战或定位 iframe。动作：ChallengeBroker 分离检测、路由、提供器和恢复状态；验收需分别统计误报和漏报。
3. **页面消失不等于业务成功。** 页面可伪造成功提示，OCR 提交也可能超时或结果未知。动作：状态命名为 `resolved_unverified`，后续必须验证业务结果；完整版本引入权威结果信号。
4. **断点恢复可能重复非幂等动作。** 保存 URL 不足以恢复任务。动作：当前记录最后成功动作和 origin；发布、支付、删除等动作恢复前必须重新确认，完整版本补幂等键和页面 generation。
5. **人工接管与 MCP 超时冲突。** 分钟级人工操作不能放在同步工具调用内。动作：使用挑战任务 ID、状态轮询和驾驶舱按钮，不长阻塞 MCP。
6. **持久登录态放大提示词注入影响。** 单一 profile 中的恶意页面可能借助高权限能力影响其他账号。动作：使用独立 profile；完整版本按账号/任务隔离，高权限能力默认不开放。

### 重大问题

- OCR 置信度不能未校准就解释为正确率；首版不暴露“正确率”承诺，只执行一次并进入结果验证。
- 尝试预算需覆盖挑战实例、账号、站点和时间窗口；当前仅实现实例级 OCR/AI 预算，属遗留项。
- OCR 图片和模型依赖带来解析、资源与供应链风险；当前使用独立进程、字节上限和超时，尚缺低权限/断网沙箱、模型哈希和 SBOM。
- OCR 文本可能携带提示词注入；答案不返回模型，不写入普通审计。
- 人工接管可能遭遇假挑战钓鱼；接管界面必须显示真实 origin，自动化在接管期间暂停。
- 完整 neo `run` SDK 与标签/文件/截图兼容的工作量独立于浏览器执行器，不能用 granular 工具成功推断迁移完成。
- 可插拔模型若不限制输入输出与出网，会扩大而不是缩小攻击面；提供器必须声明版本、数据出网和运行时。

### 最险场景

恶意页面在持久登录会话中伪造挑战或业务成功状态，诱使 AI/人工完成身份核验，随后利用旧检查点重复执行高风险动作；若截图、OCR 文本或审计同时泄露敏感内容，影响会扩展到多个账号。

### 被剔除的无效反驳

- “所有 OCR 都必然失败”：绝对化且可被授权文字挑战样本证伪。
- “本地 OCR 必然远程泄密”：本地运行与日志/模型上下文风险应区分，不能虚构网络外传。
- “人工接管等于方案失败”：是否可接受取决于接管率和任务 SLA。
- “统一 Broker 必然是 god object”：模块边界可拆分，不能仅按名称判定。
- “通用绕过第三方风控”：已从实现目标剔除，不作为过时靶子继续讨论。

### 方案级反转条件

出现以下任一情况，停止当前自动挑战路线，退回检测 + AI + 人工：

1. 授权测试中出现 OCR 导致的账号锁定或重复不可逆提交。
2. 100 次中断恢复测试出现任何重复发布、支付、删除等副作用。
3. 人工接管期间仍能自动读取敏感页面或剪贴板。
4. 目标工作流中人工接管率超过 50%，或 OCR + AI 未减少至少 20% 的人工操作时间。
5. 未授权远程能力能够在审计外发送页面、截图、Cookie 或文件。
6. neo 高频任务双跑显示新执行器成功率持续更低，且兼容成本超过独立产品收益。

## Stage 2：切换支持视角

视角已切换，仅陈述方案成立的理由与最小前提。

1. **已有基础设施足以验证核心价值。** Chromium/CDP 提供真实输入和页面控制，MCP SDK 提供标准客户端通道，`ddddocr` 可本地运行，无需先承担浏览器内核维护成本。
2. **低层操作下沉能直接减少模型输出。** 当前 agent 调用只需语义动作和 ref，轨迹、剪贴板、挑战重试与等待均由本地执行器承担。
3. **可插拔边界与实际代码一致。** OCR、指针、剪贴板已经通过同一 CapabilityRegistry 注册，新增模型不需要改写挑战主状态机。
4. **动作溯源不是附加日志，而是执行数据流的一部分。** 快照 ID/SHA-256、能力版本、动作前后页面和结果在同一动作路径生成。
5. **降级链符合减少人工的目标。** OCR 失败后 AI 仍可继续，只有预算耗尽或敏感身份核验才需要人工。
6. **端到端可行性已得到小规模实测。** 真实 Chrome、真实 MCP 客户端、语义动作、剪贴板、快照溯源和完整降级状态机已通过。

成立所需最小前提：高频工作流可基于 CDP 实现；持久 profile 能按任务隔离；挑战收益高于适配维护成本；审计能覆盖所有执行路径；模型能力始终受策略层约束。

## Stage 3：中立对比与结论

### 替代方案比较

- **立即 fork Chromium**：内核控制力最高，但构建、签名、安全补丁和升级成本最大；当前没有实测需求证明必须承担。
- **只做 MCP 代理、不做能力层**：实现最快，但无法形成模型路由、挑战恢复和本地动作编排的产品差异。
- **现有 Chromium + sidecar + 能力注册表**：能最快验证核心价值，保留以后增加扩展或内核改造的路径，当前优势明显。

### 结论

**有条件推进，当前候选方案相对立即 fork 的优势约为 70:30。** 依据是纵向链路已实测、组件均可替换、首阶段无需内核维护；不是依据市场预测或通用验证码成功率。

建议动作：**有条件推进 + 明确止损线**。继续完善 P0/P1，不启动 Chromium fork，不宣称完整替代 neo，不将通用 OCR 路径描述为生产级全类型挑战能力。

### 最大未知风险

不是 OCR 准确率，而是**不可信页面、持久登录态、高权限能力和自动恢复组合后，是否会出现现有测试无法发现的跨账号副作用**。该风险必须通过多账号隔离、故障注入和真实角色矩阵验证，无法靠架构文档消除。

### 证据等级

- 真实 Chrome/MCP/动作/剪贴板/降级状态机：本地端到端已复核。
- `ddddocr` 通用能力：官方项目说明与本地环境验证；目标站点准确率未验证。
- 全类型挑战覆盖、生产级安全、完整 neo 替代：未验证，不列为既成事实。
- 红队成本量级：工程估算，未作为项目报价或排期事实。

## 补充决策：首个开源版采用 Electron

### Stage 1 复核结论

独立红队指出：stock Chrome 原型不能证明独立 App 可交付；Electron 扩展兼容不是完整 Chrome 兼容；内嵌 CDP/MCP 必须防止绕过能力策略；密码与活跃会话不能按整 Profile 复制承诺；安装、签名、更新和安全补丁属于首发平台成本。上述问题均保留为平台验收闸门。

### Stage 2 支持视角

Electron 能最快复用现有 Node 执行引擎、MCP、能力注册表和审计模型，并提供独立窗口、WebContentsView、Profile 与安装生态。真实 Electron 端到端测试已证明网页标签、语义动作、虚拟剪贴板和快照溯源可迁移，不只是窗口演示。保留 stock Chrome 对照适配器可继续验证底座无关性。

### Stage 3 决策

按使用方明确选择，**首个开源版有条件推进 Electron**。不同时建设第二套 App UI，不把 Electron 密码本/扩展能力描述为 Chrome 完整兼容。后续 Chromium/BrowserOS 底座必须复用 MCP、能力协议、挑战状态机和审计格式。

止损与反转条件：Electron 无法承载核心网页工作流；Profile 数据无法稳定迁移到统一格式；必须通过暴露未认证 CDP 才能提供核心能力；原生密码本或关键平台能力形成无法回退的双套实现；安装/更新/安全补丁成本超过持续预算。出现上述情况时停止 Electron 平台扩张，保留执行引擎并切换底座。
